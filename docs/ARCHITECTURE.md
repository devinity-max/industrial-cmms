# Proposed architecture and interface contract v0.1
Decision status: provisional until both developers approve the cloud-development stack; hosting separately requires IT approval. Prefer a modular monolith, not microservices. React + TypeScript + Vite frontend, PostgreSQL + managed Supabase Auth/DB in a dedicated synthetic-only development project; native Windows client tooling, no local container runtime required; server-side RPC/Edge Functions for sensitive mutations and scheduled work, private object storage. QR generated using vetted open-source library. Vitest + Playwright and SQL/RLS integration tests. No native app/PWA required for demo. Select supported stable dependency versions at bootstrap and lock them; do not use floating latest versions in CI. Use UTC instants and an approved plant-local operational calendar (demo Asia/Kolkata). No live integration or credentials. References: https://supabase.com/docs/guides/local-development/cli/getting-started ; https://supabase.com/docs/guides/local-development/cli-workflows .

## Logical structure (not executable schema)
- plants(id, name, timezone); departments(id, plant_id, name); assets(id UUID immutable, plant_id, department_id, machine_number, name, qr_token UUID immutable unique, status, technical metadata, version). Provisional uniqueness plant+machine_number; confirm with client. Enforce consistent plant/dept relationships. Never reuse retired identifiers or QR tokens.
- profiles(user_id from auth, display_name, enabled); memberships(user_id, scope, role). Implement explicit plant or asset scope; test all paths. Roles viewer/admin for demo. Do not trust mutable auth user metadata. User management by privileged service only.
- daily_obligations(id, asset_id, operational_date, shift_key non-null explicit sentinel when no shift, due_at, rule_version, state). Unique asset/date/shift/rule as agreed; demo one per asset/day. Define eligibility independently of activity logs. Schedule revisions do not alter historical obligations silently.
- daily_submissions(id, obligation_id, version, status, submitted_by, submitted_at); daily_activities(id, submission_id, started_at, ended_at, category, activity, observation, action, spare_text, work_status, remarks). One canonical current submission per obligation, historical revisions retained. Demo completion criteria provisional; do not label maintenance as approved if not verified.
- audit_events(id, actor_id or service identity, target_type, target_id, event_type, old/new approved snapshots, reason, created_at). Server-generated append-only to ordinary users; privileged access restricted. Exclude secrets and minimize sensitive payloads.
- notification_events(id, obligation_id, recipient_id, channel, escalation_step, status, created_at, resolved_at); unique idempotency tuple obligation/recipient/channel/step. delivery_attempts record outcomes, retry state and provider ID. Separate alert resolution from delivery status. Test only with a simulated delivery adapter or approved isolated mail sink.
- Later: versioned checklist templates/items, PM plans/work orders, JH submissions, abnormalities, breakdowns, parts, modifications, approvals, documents, transfer history. Do not implement these tables just because listed; design in slice after rules confirmed.

All tables have keys, foreign keys, scope enforcement and indexes for common queries. Use constraints for uniqueness and timestamps; transactions for updates + audit and resolution; optimistic locking or equivalent concurrency control. Model history from authoritative records/revisions, not duplicated editable cards. Use migrations, deterministic test seeds and rollback/recovery plans. Only store generic approved metadata in flexible JSON; validate its schema, not unstructured entire system.

## Contract for first slice (logical operations, backend owner maps to RLS-protected queries/RPCs; do not build two parallel APIs)
| Operation | Input | Output | Permission |
|---|---|---|---|
| signIn | approved login identifier + password | managed session | provisioned account |
| getAuthState / onAuthStateChange | current managed session / listener | auth snapshot / unsubscribe | local lifecycle |
| signOut | current session | confirmed sign-out or sanitized error | current account |
| listAssets | cursor, optional filter and page size | scoped items and nextCursor | viewer/admin |
| getAssetByQr | qr_token | AssetDetail or generic not found/denied | viewer/admin with asset scope |
| listHistory | assetId, cursor | scoped HistoryItem[] | viewer/admin |
| getDailyObligation (provisional M2) | assetId, operationalDate | DailyObligation or none | viewer/admin |
| submitDaily (provisional M2) | obligationId, expectedVersion, requestId, activities, reason if revision | persisted submission id/version/status/time | scoped admin |
| listAlerts (provisional M3) | cursor | scoped NotificationSummary[] | approved recipient/admin |

Shared TS contract lives in `src/contracts/`. AssetSummary: id, machineNumber, name, department, displayStatus (unknown unless recorded); AssetDetail adds qrToken, approved fields. HistoryItem: id, assetId, kind, occurredAt, summary, actorDisplay, version. DailyObligation: id, assetId, operationalDate, dueAt, state, version. ActivityInput: startedAt/endedAt ISO timestamps or null, category, activity, observation, action, spareText, workStatus, remarks. Error shape `{code,message,requestId}` with sanitized message; code UNAUTHENTICATED, NOT_FOUND_OR_DENIED, VALIDATION, CONFLICT, TEMPORARY_FAILURE. Never expose raw DB errors. API semantics and exact TS types finalized by both owners before parallel work. Do not expose a service key, role selector or mock fallback in real app. Mock adapter only explicitly enabled in local tests; fail closed otherwise.

### M1 contract for developer review

[The shared contract](../src/contracts/index.ts) separates M1 from provisional M2/M3 operations. M1 implementations and test fixtures implement only `CmmsAdapter`.

- **Session lifecycle.** Restore with `getAuthState()`. Subscription delivers the current snapshot first and then ordered changes, including changes in other tabs, until unsubscribed. A verified session exposes only the user ID. No session yields `signed_out`. A session that expired and cannot be renewed because credentials are invalid yields `expired` and requires login. A network or provider outage yields a sanitized `TEMPORARY_FAILURE` and permits retry. Until verification succeeds, withhold protected content. On loss or change of identity discard cached asset data, capabilities and stale in-flight results.
- **Sign-out.** Immediately lock protected UI, clear local session material and cached records across tabs, and request provider invalidation of the current session's refresh capability. Report success only on confirmed invalidation or an already absent session. On uncertain remote completion return `TEMPORARY_FAILURE`, keep the client signed out and do not claim remote revocation.
- **Asset detail.** On authorized lookup the server computes `capabilities.canManageAsset` for the returned asset using active memberships for that machine and its owning plant. Never reuse this decision on another asset. Capabilities guide display only. Every read and mutation independently enforces scope through RLS and server-side checks. An inaccessible or missing asset yields `NOT_FOUND_OR_DENIED`.
- **Asset pages.** Omit the cursor on the first request. Page size defaults to 25 and accepts 10, 25 or 50. The server rejects other sizes with `VALIDATION`. Apply current scope and filter before keyset pagination by immutable asset UUID ascending. Return a non-null opaque cursor only when more matching rows exist. Bind continuation to caller and query, reject invalid or mismatched cursors, and restart pagination on filter or size changes. Each page reflects current permissions.

Instants use UTC ISO 8601 strings. Operational dates use plant-local YYYY-MM-DD. The daily receipt carries the persisted version and server timestamp. Status vocabularies, additional asset fields and ledger validation rules await owner review. The interface grants no permissions. Developers A and B must agree on these signatures before parallel implementation.

## Reminder design
A scheduled server job finds eligible overdue obligations; transaction creates one alert/outbox per approved recipient and stage, no duplicates. Worker claims pending deliveries safely, rechecks obligation before sending, uses provider idempotency where supported, logs failures and retries with bounds. On submission, resolve internal alerts and cancel unsent work; an already delivered message cannot be recalled. Scheduler runs independently of open browser. Monitor job heartbeat. Demo uses simulated clock and fake delivery adapter or approved isolated mail sink, real email/WhatsApp disabled. Configure deadlines, recipients, calendars and escalation only after approval. Do not send confidential details or access tokens in external messages. Links still require login. No WhatsApp Web automation; official approved platform only. Production exact-once delivery cannot be guaranteed across provider failures.

Coordinate documentation changes.

## Hosted development workflow (v1.1)
- FND-01 runs without a hosted backend, credentials or container runtime. Pin compatible dependencies; CI builds and tests without secrets. A test-only fixture must never be a runtime fallback.
- Developer A manually provisions the approved synthetic development project. Keep project URL and browser publishable key in ignored .env.local (example names VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY). Publishable key is not an authorization boundary. Never put secret/service-role keys, database passwords or access tokens in VITE_ variables, Git or prompts. Disable public signup; provision individual fictional test accounts.
- Store all schema and policy changes in versioned supabase/migrations/. Review PR, verify linked project reference, inspect migration history and dry-run the remote push before any approved apply. Use pinned CLI syntax verified against current docs; no remote reset, undocumented dashboard schema changes or agent-run automatic remote mutations. Commands requiring containers run only in disposable CI environments, if approved.
- Test schema from scratch and RLS with real auth identities in an isolated disposable test database or separate approved test project. Never run destructive tests against shared dev/staging/production. Record real results, keep failed/unrun tests visible. No production release until repeatable integration, migration and restore tests pass.
- Keep dev, staging and production projects and credentials separate. Only dev is contemplated initially. Test remote delivery using fake recipients/adapters; no external real messages unless authorized. Free development tiers may pause or have quotas; production sizing and IT approval remain open.
