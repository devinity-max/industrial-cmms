# M1 migration and test runbook

Developer A applies reviewed SQL only after explicit authorization naming the isolated synthetic project, the commit, migrations and fixture operations. Verify the project reference against the dashboard independently of local configuration. Never use a shared project for the destructive-condition tests.

1. Confirm a restorable backup or disposable empty test target. Disable public signup and anonymous sign-ins. Restrict administrative accounts and enable MFA. Expose only the intended Data API schema (public for the M1 RPCs). Exclude cmms from exposed schemas and inspect existing public functions, grants, views, GraphQL and publication settings for alternate access paths.
2. Record the approved CLI version and target, inspect migration history, then review the output of `supabase db push --dry-run` against the verified linked test target. Stop on drift or extra changes. Developer A alone applies the approved plan. Use the migration runner's per-file transaction. Never run the statements interactively in autocommit mode because functions and grants must become visible together.
3. Apply **20261127000100_m1_storage.sql** before **20261127000200_m1_reads.sql**. The first creates private tables, identity constraints and read-only RLS. The second grants authenticated execution on four invoker RPCs. Scope comes from active database memberships and profiles. Plant-scoped machine-number uniqueness is provisional. Every page rechecks current scope. Asset pagination supports literal case-insensitive substring matching on name/number up to 128 characters. A revoked or changed cursor anchor requires restarting the query. History returns pages of 25, newest occurred_at first, with descending UUID for ties. The continuation compares both values. The transaction in constraints.sql tests a timestamp tie across the 25-row boundary.
4. For the fixture test only, Developer A uses the Auth dashboard's create-user operation with confirmed email, without invitations or outbound mail. Create four separate accounts at example.invalid with local parts m1-viewer, m1-admin, m1-machine and m1-south. Generate separate random passwords and deliver each privately to its designated tester. Never use shared admin credentials, real addresses, or secrets in arguments, source or logs. No profile or membership is granted automatically on Auth creation.
5. In the isolated approved target run **supabase/tests/synthetic.sql** once as setup owner. It links the four existing Auth IDs and inserts two robots plus paging and cross-plant controls. Duplicate setup fails atomically. Run **supabase/tests/constraints.sql** in one connection with stop-on-error. It rolls back its changes and explicitly assumes the ordinary authenticated role for auth checks. Its impersonated subject test supplements real Auth testing.
6. From Windows in the repo root, supply process-only M1_APPROVED_TEST_REF, M1_TEST_URL, M1_PUBLISHABLE_KEY and individual M1_VIEWER_PASSWORD, M1_ADMIN_PASSWORD, M1_MACHINE_PASSWORD, M1_SOUTH_PASSWORD from an approved secure store. Run `node supabase/tests/verify-hosted.mjs` only with approval for fixture sign-ins and sign-outs. Exit 0 means the HTTP assertions passed. It checks direct read scopes, capability differences, continuation and private-schema isolation (PGRST106). Table write grants and actual UPDATE denial are tested separately under the authenticated PostgreSQL role in constraints.sql. Clear credentials from the process afterwards. No service key is required.
7. To test deactivation with a real unexpired JWT, authorize a temporary change to the isolated viewer profile and its restoration. Set `$env:M1_TEST_DISABLE_VIEWER = '1'` and run the hosted runner in an interactive terminal. At its pause, Developer A verifies the project and the fixture user's UUID against Auth, then commits an update setting only that user's cmms.profiles.enabled to false. Confirm exactly one row changed and type `disabled`. The runner reuses the original bearer string and requires HTTP 403 / SQLSTATE 42501 before expiry. Restore the Viewer to its previous enabled state even if an assertion fails. Verify restoration, type `restored`, and confirm a successful read using the same still-valid JWT. Remove the test flag. If no change was made and the operator is unavailable, type `pending`. If the JWT expired, record the incomplete result and obtain approval before repeating the mutation. Separately verify two-tab logout, delayed reads and browser-back handling with the integrated frontend.
8. On failure stop applying changes. Preserve migration history and test evidence. Lock access by disabling affected profiles or revoking M1 RPC execution through a reviewed corrective migration. Prefer a forward fix and repeat verification. Restore a backup into a separate approved target if recovery is needed. Never drop shared records, rewrite applied migrations or reset a shared database.
